## Сверка с настоящим КриптоПро

Владелец, 2026-10-29: `dump-fields.js` и `check-api.js` с КриптоПро CSP 5.0.13800 и плагином 2.0.15700 под Linux,
ru_RU.UTF-8 (`JOURNAL.md`, 2026-10-29). Названные им расхождения — формат `RawSignature`, `Value` атрибутов подписанта,
1/0 в объектах сертификата, `FriendlyName` расширений, регистр в `Find` по корню — с 1.15.3 как у КриптоПро (по его
описанию: сами образцы до агента не дошли). Не трогали: версии и провайдер в `About` (константы совместимости);
`PrivateKey.ProviderType` — у нас нет, у КриптоПро для HDIMAGE 80, для Рутокена данных нет; `CachePin` у КриптоПро для
HDIMAGE не поддерживается, для Рутокена данных нет. Названия расширений известны только для семи OID и локали
ru_RU. XAdES-BES самого КриптоПро наша проверка принимает (владелец); `verify_xmldsig.py` с 1.15.3 принимает подпись,
устроенную так же (`xades.spec.ts`), сам образец владельца через неё не прогоняли.

Не сверено, сделано по документации КриптоПро и Microsoft: поля считывателей и контейнеров; XML-шифрование (формат — из
КриптоПро .NET и форума); проверку наших CAdES-T и XAdES самим КриптоПро владелец не присылал. Сверка — раздел «Сверка
полей с КриптоПро» `MANUAL-CHECK.md`.

## Известные проблемы

- Firefox: файл расширения не подписан Mozilla — обычный Firefox ставит его только до перезапуска
  (`MANUAL-CHECK.md`); сайт с нестандартным портом включается для всех портов узла (Firefox не подставляет скрипты
  по адресу с портом); пока под WebDriver BiDi открыта вкладка расширения, адаптер Рутокена отвечает секундами (без
  BiDi не проверялось, `JOURNAL.md`).
- `HasPrivateKey()` до первого PIN на странице — `true` для сертификатов пользователя. `IsValid()` без галочки расширенной проверки
  смотрит только сроки. С галочкой цепочка без издателя в наших хранилищах — один сертификат без причины:
  промежуточные и корневые по ссылкам из сертификата (AIA) не скачиваются. `CheckCertificate` проверяет только сроки.
- Выпуск сертификата: сертификаты УЦ из ответа ставятся только после «Да» на вопрос о корневом (галочка
  включена), без корневого в ответе — не ставятся; ключ
  «подпись и обмен» (выбор страницы по умолчанию) экспортные Рутокен ЭЦП 3.0 не создают — тогда нужен «ключ
  подписи»; эмулированы только объекты, которые вызывает certsrv.
- Вход ИП — на lkipgost2.nalog.ru, только по ГОСТ TLS, из Chrome недоступен.
- Нет `CoSignCades`: сайты действия 14 вызывают его для документов, не для входа.
- Проверка подписи: отзыв сертификатов не проверяется (решение владельца 2026-09-24; КриптоПро без списка отзыва
  отказывает `0x800B010E`); промежуточные УЦ — из самой подписи и из второй вкладки хранилища, из интернета (AIA) не загружаются; CAdES-T и X Long не проверяются
  (`0x80004001`), подписи RSA тоже; `GetMsgType` называет подписи X Long и A типом CAdES-T (не сверено).
- `SignedXML`: Base64 в `Content` — только документы в UTF-8; преобразования — только enveloped-signature и C14N;
  ссылки `#id` находят кроме `xml:id` ещё `Id`/`ID`/`id` (настоящий плагин — только `xml:id`); в `KeyInfo` — только
  сертификат подписанта, как у КриптоПро по документации `ISignedXML::Sign`.
- Шифрование (`JOURNAL.md`, 2026-10-08): Рутокен Плагин шифрует только после ввода PIN; сообщения «Магмой» длиннее 1 КБ и
  «Кузнечиком» длиннее 4 КБ OpenSSL с GOST-движком 3.0.2 расшифровывает иначе, чем Рутокен (разный размер секции
  CTR-ACPKM), как поступает КриптоПро — не проверено; на webtools.html получателем можно выбрать только сертификат с
  токена (хранилище «Другие пользователи» у нас пустое).
- XML-шифрование: только ГОСТ 28147-89 (режим CBC без преобразования ключа, набор параметров Z) и ключи ГОСТ Р
  34.10-2012; `derive` на настоящем Рутокене нашим расширением не проверен (по документации форка `derive` Рутокен
  ЭЦП 3.0 даёт то же значение VKO, `JOURNAL.md`, 2026-10-20); расшифровываются только `EncryptedKey` с сертификатом
  получателя (`X509Certificate`), все `EncryptedData` документа — для сертификатов одного токена.
- Контейнеры — только ключи, которые видит Рутокен Плагин: контейнеров формата КриптоПро на Рутокене нет;
  webtools.html перечисляет контейнеры сразу при открытии, поэтому PIN спрашивается при загрузке страницы.
- XAdES: `SigningCertificate`, а не V2; штамп XAdES-T в подписи по шаблону ставим (КриптоПро, по сообщению с форума,
  не ставит). Шаблон со своими `QualifyingProperties` заполняется как есть, XAdES-T добавляет в них штамп. Штамп при
  подписи проверяется только на оттиск и nonce, подпись службы — нет (как у CAdES-T); `Verify` штамп XAdES-T не
  проверяет. XAdES-X Long Type 1 и XAdES-A — понятный отказ.
- webtools.html (обход 2026-10-08, `JOURNAL.md`): любой отказ проверки CMS страница показывает как `0x8009100E`,
  CAdES-T — как успешную проверку CAdES-BES; подпись без сертификата (цепочка «Нет») наша проверка не проверяет;
  «Удалить сертификат» — `oStore.Remove is not a function`; чужой сертификат из файла спрашивает PIN и на миг пишется
  на токен. Очередь операций с токеном — в пределах страницы: на стенде у каждой вкладки свой процесс Рутокен
  Плагина и свой вход на токен, вкладки друг другу не мешают (`JOURNAL.md`, 2026-10-16); на устройстве не проверено.
- CAdES-X Long и CAdES-A не поддерживаются (этап 6). CAdES-T: штамп при подписи не проверяется (решение владельца
  2026-10-08); без атрибутов сайта штамп получает Рутокен Плагин, и служба — только по HTTP (так он умеет), с
  атрибутами — расширение, по HTTP и HTTPS.
- `CADESCOM_AUTHENTICATED_ATTRIBUTE_MACHINE_INFO` — отказ `0x80004001`. `RawSignature` без сертификата (выбор
  сертификата, как в Windows) — отказ. `EncodedData.Format` и `Decoder` — `0x80004001`.
